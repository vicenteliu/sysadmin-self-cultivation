# Lab —— "每五十个用户一个人"在这里是对的，而它说不出理由

> 🌐 **语言：** [English（默认）](../../../../../cross-cutting/labs/help-desk-queue/README.md) · **中文**
>

**目标：** 把人力配置这个问题变成你能跟它辩论的算术。第 13 步问一个一百人的服务台需要多少人。
通常的答案是一个比例，而一个比例是一句关于一个非线性系统的线性句子。

**你会练到：** [build-out 第 13 步](../../../build-out/13-the-help-desk.md)所要求的东西 ——
一个**附着推理过程**的人力数字，包括它对第 04、08 和 15 步所建的那些自动化做了什么假设。

七个工单类别，各有各的到达率和处理时长；两个世界（那些自动化建了，或者没建）；在一个写明的支持窗口
上跑 Erlang-C。那个比例和这个模型在一百人处一致。它们的一致是偶然的，而这个模型说得出那次偶然在
哪儿结束。

**这些速率所描述的那间办公室，就是
[参考办公室](../../../the-reference-office.md#parameters)**，它现在写明了那个窗口和那些工单量，
并把人力配置这个问题指回这里 —— 因为这个模型算的是一个*地板*，并且说得出那个地板在哪儿失效，
而一个待在参数表里的人头数会活得比那条限定条件还久。这次配对掉出来一次交叉核对：在那个自动化过的
世界里，这个模型把纳管和装机放在一年大约五十三张工单上，而参考办公室的更新周期在同一年里独立地
产出了大约 **六十二次设备交接**。八次交接对七张工单，来自两条不共享任何输入的推导。

## 这个模型是什么，不是什么

Erlang-C 假设 Poisson 到达、指数分布的处理时长、没有放弃排队，以及只接工单什么别的都不干的坐席。
真实的处理时长比那个更偏斜，而真实的坐席有项目要做。所以**那条曲线的形状是稳健的，而那些精确的
分钟数不是。**

更要紧的是：这个演练算出来的是一个**地板**，不是一份人力配置建议。它给工单定价。它看不见项目工作、
维护窗口、走到工位旁边的打断、二线升级、更多站点或者非工作时段，而一个真实的服务台合理地就是比它
的工单负载要大。把它读成"你们人配多了"，就是把这个模型读错了 —— 而这也是为什么在规模那一节的对比
里，那个比例被刻意拿掉了。

39% 的利用率并不意味着 61% 在闲着。它意味着一周里有 61% 可以用在这份工作所包含的其他一切上。

## 这个 lab 为什么是纯本地的

排队论就是算术。整个论证就是七个类别、两个世界，和一个自 1917 年起就存在于容量规划里的公式。
不用工单系统、不用数据导出、不用凭据、不用 `pip install`。Python 标准库，CI 也跑得了。

## 跑它

```bash
python3 cross-cutting/labs/help-desk-queue/queue_drill.py
```

exit code `0` 表示关于这个教训的每一条断言都成立。

## 你会看到什么

1. **自动化削减工单的速度，比它削减工作的速度快。** 工单掉了 **39%**，工作小时掉了 **31%**，
   而平均处理时长**上升**了，21.6 → 24.7 分钟。密码重置是六分钟，权限问题是二十二分钟；自动化先
   拿走的是那些短的类别。工单数是那个最会夸大你省下了多少的单一指标。
2. **等待时间会拐弯。** 在那个自动化过的世界里，一百人时：

   | 坐席数 | 利用率 | p95 等待 |
   |---|---|---|
   | 1 | 39% | 84 分钟 |
   | 2 | 20% | 4 分钟 |
   | 3 | 13% | 0 分钟 |

   多一个人是**好 21 倍**，不是好两倍。排队延迟随利用率呈双曲线上升。这恰恰是一个按人头算的比例
   没有任何办法表达的东西。
3. **前面那些步骤把人折算进去了。** 一个坐席在没有那些自动化时能满足目标到 **135** 人，有了之后
   是 **185** 人 —— 同一个服务台多扛了 50 个人，代价是每周被移除的 **8.7** 小时工单工作。那就是
   第 04、08 和 15 步的价值，用人力配置这场对话真正在用的那个单位说出来。
4. **在一百人处，那个约束是覆盖，不是工单量。** 工单量需要 1 个坐席。一个 50 小时的支持窗口对上
   一周 40 小时，需要 2 个。那个比例也说 2 —— 它在没有任何一个能告诉它这件事的输入的情况下，落在了
   对的数字上。
5. **那个地板会随估算面移动；一个比例不会。** 从 **350** 人开始，那两个世界需要不同的服务台：
   同一家公司、同样的人头数，答案取决于那些自动化建没建。一个仅从人头数推导出来的数字表示不了这
   件事，因为那个输入根本不在它里面。

## 验证（别光信这个脚本说的）

```bash
python3 .../queue_drill.py --break-it   # exit 1
```

`--break-it` 用那个"每五十人一个"的比例、而不是用排队来配人。注意什么*没有*发生：它并没有产出一个
荒谬的数字。在一百人处它产出的是**和这个模型一样的 2**。三条断言照样挂掉了，而它们才是有意思的
那几条 —— 那个比例点不出它的约束是什么、说不出它的答案在哪个人口规模上失效，而且不管那些自动化
存不存在，它返回的都是同一个人头数。

那才是值得内化的那个失败：**这个比例在这里不是错的，它在这里是不可证伪的。** 在这个数字不再为真
之后很久，它还会继续产出一个数字，而它里面没有任何东西能告诉你那件事已经发生了。

想再往前一步，把那三个自动化类别的 `remaining` 设成 `1.00` —— 也就是第 04、08 和 15 步从来没被建
起来的那个世界。一个人的天花板从 185 掉到 135，而这个演练会带着**四**条挂掉的断言 `1` 退出，
而不是安静地报出一个更小的数字。那是正确的，也值得注意：这个 lab 五条主张里有四条是*关于那些自动
化*的主张，所以把它删掉并不会改变一个数字，而是把被测量的那样东西移除了。那个比例的答案，当然，
一动不动。

## 重点

**一个人力配置数字不是一个数字。** 它是一个数字、它所来自的那片估算面，以及它所假定的那些自动化
—— 而只有后两样能在下一个问题面前活下来。

三件要带走的事：

- **绝不要在不带那两条假设的情况下引用那个人头数。** "两个人"不是一个答案；"两个人，在这片估算面
  上，假定零接触纳管和自动化的入转离"才是，因为它告诉了下一个人什么会改变它。
- **工单数是自动化的错误成功指标。** 报告被移除的小时数和平均处理时长的变化，否则你会为一次 31%
  的胜利宣称 39%，然后在服务台并没有感觉更空的时候吃一惊。
- **搞清楚哪个约束在绑着。** 如果是覆盖，那么工单量再涨也什么都不改变，直到它突然改变一切 ——
  而你正在用的那个比例看不见那个交叉点正在到来。
