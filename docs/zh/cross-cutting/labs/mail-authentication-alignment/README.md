# Lab —— "记录都发布了"和"这个域名受保护了"不是同一句声称

> 🌐 **语言：** [English（默认）](../../../../../cross-cutting/labs/mail-authentication-alignment/README.md) · **中文**
>
> ⚠️ 本项目**默认语言为英文**，`cross-cutting/labs/mail-authentication-alignment/README.md` 是"事实来源"。本页中文是多语言支持的一部分，可能略滞后于英文版；两者不一致时以英文为准。

---

**目标：** 把那两句话之间的缺口变得可测量。SPF、DKIM 和 DMARC 都发布了，每一个检查工具都返回绿色，
而这个域名仍然完全可以被伪造 —— 不是通过一个奇异的故障，而是通过那个几乎每一个域名此刻都坐在里面
的普通故障。

**你会练到：** [build-out 第 06 步](../../../build-out/06-tenant-and-mail.md)所坚持的东西 ——
把每一个以你的名义发信的东西都枚举出来，并且在一个写下来的日期上从 `p=none` 挪走。

一间一百人的办公室把三条记录都发布了。那些聚合报告到了。没有人在撒谎，而且以一个检查工具看得见的
方式，没有任何东西配错了。在一个报告窗口里，**有 640 封伪造邮件带着这个域名出现在 `From:` 行里被
投递了**，而有两个部门离一次没有人警告过他们的策略变更所引发的故障，只有一步之遥。

## 这个 lab 为什么是纯本地的

邮件认证是一个*协议*问题，不是一个厂商问题。SPF 认证的是信封域名，DKIM 认证的是签名域名，而 DMARC
问的是它们两个都回答不了的第三个问题：那个被认证过的域名，和人真正会读到的那个 `From:` 头对得上
吗？那层关系 —— **对齐** —— 完全可以用一个模型表达出来：发信方带着一个信封域名、一个签名域名、
一条发布了或者没发布的 SPF 路径，以及一个消息量。

不用租户、不用 DNS、不用注册商、不用凭据、不用 `pip install`。Python 标准库，CI 也跑得了。

## 跑它

```bash
python3 cross-cutting/labs/mail-authentication-alignment/dmarc_drill.py
```

exit code `0` 表示关于这个教训的每一条断言都成立。

## 你会看到什么

1. **三个绿勾，外加 `p=none`。** 那个检查工具确认了那些记录*存在*。它从来没读过那条策略。这是一次
   真实的检查，在回答一个比它看起来更小的问题，而工作就停在了这儿。
2. **两个事实来源在两个方向上互相不一致。** 那份发信方清册列了 **4** 个；那份聚合报告显示 **6** 个。
   有两个真实的发信方从来没被列进去 —— 其中一个是财务的，也正是第 06 步预先点名的那个结果 ——
   而有一个被列出来的发信方已经根本不发信了。哪份清单都不是真相。那份报告只是两者里更诚实的那个。
3. **"通过"和"对齐"是两个不同的词。** 那个工单系统 SPF **通过**、DKIM **也通过**，
   **而 DMARC 失败**：两次认证都是真的，而且两次都是给那个厂商的域名做的，不是给你的。两个绿勾，
   没有对齐，没有通过。
4. **那个伪造者的 SPF 也通过。** 在他自己的信封域名上，用他自己发布的记录。"SPF 通过了"是一句关于
   *某个*域名的陈述，不一定是关于你的 —— 对齐是唯一逮得住他们的东西。
5. **`p=none` 把它们全都一模一样地投递出去。** 对齐的、没对齐的和伪造的：同一个处置。那条策略并没
   有对它花了一个季度算出来的那个判定采取任何行动。
6. **执行的风险在你承担它之前就可以测量。** 今天挪到 `p=quarantine` 会打断 **3** 个合法发信方 ——
   而且*恰恰*就是那份清册搞错了的那几个。先把枚举修好，`p=reject` 就打断 **0** 个，同时把全部 640
   封伪造邮件退回。

## 验证（别光信这个脚本说的）

```bash
python3 .../dmarc_drill.py --break-it   # exit 1
```

`--break-it` 只按认证结果去求值，从不把它们和 `From:` 域名做比较 —— **也就是邮件健康检查工具汇报
的方式，以及这些报告实际被阅读的方式。** 那个没对齐的工单系统变绿了，那个伪造者也是。输出里最锋利
的那一行是最后那张表：在 `--break-it` 之下，`p=reject` 照样把那些伪造邮件投递出去。可用的最严格的
策略，按标准方式去读，什么都拦不住。

这个演练会带着被点名的那四条挂掉的断言 `1` 退出。

想再往前一步，把那个工单系统的 `in_spf_record` 设成 `True` —— *把那个厂商加进你的 SPF 记录*，
也就是几乎所有人第一时间会伸手去够的那个修法。什么都不动：它本来就在那个厂商自己的域名上通过 SPF，
而往你的记录里加一条路径，并不会让他们的域名变成你的。这个演练仍然 `0` 退出，而那个发信方仍然
失败。对齐不是一个 SPF 问题，所以它没有一个 SPF 的修法。

## 重点

**`p=none` 是一份监控配置，而它被广泛地误当成一项安全控制。** 它产出报告、仪表盘变绿，而世界上
任何一个人仍然能以你的域名发信 —— 这也是为什么"我们有 DMARC"需要一个关于那个策略值的追问。

三件要带走的事：

- **有两次认证和一次对齐。** 完美的 SPF 加完美的 DKIM，两个都没对齐，就是一封失败的邮件和一张通过
  的截图。
- **那份清册是一句声称；那份报告是证据。** 它们会在两个方向上不一致，而把它们对上是一个人的活 ——
  那些报告可以被机器分组和解释，但哪些发信方是*被授权的*，是一个决定。
- **执行之所以被推迟，那个理由是真实而有限的。** 它会打断你没能枚举出来的那些发信方 —— 一份可知的
  清单、这一周的活，不是一份没有尽头的危险。
