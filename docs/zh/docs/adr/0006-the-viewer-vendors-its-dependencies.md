# 这个 viewer 把依赖 vendor 进来，而不是采用一个站点生成器

> 🌐 **语言：** [English（默认）](../../../../docs/adr/0006-the-viewer-vendors-its-dependencies.md) · **中文**
>

这个仓库里提交了一个 2.5 MB 的压缩 JavaScript 包
（[`site/vendor/mermaid.min.js`](../../site/README.md)）。它比这里所有 Markdown 文件加起来还大，
而且是这棵树里最让人意外的那一样东西，所以它需要一个被记录在案的理由。

它所出自的那条需求：这个站点必须能以**两种方式**启动 —— 直接启动，以及在容器里启动 —— 而那条
直接路径必须是*一条命令，什么都不用装*。

## 决定

**这个 viewer 是手工建的、对内容没有构建步骤，并且把它那两个运行时库带在树里。**
`python3 site/serve.py` 就是那条直接路径的全部：没有 `pip install`、没有 `npm install`、不联网。
Markdown 在浏览器里渲染；唯一被生成的产物是一份标题映射和一份搜索语料，两者都由一个标准库的
Python 脚本产出。

## 考虑过的选项

- **MkDocs Material。** 最强的那个替代方案，也是如果这个决定将来被重新审视时该去够的那一个：
  它是 Python 原生的，和一个已经是 Markdown 加 Python 加 shell 的仓库很搭，并且免费带来搜索、
  导航、i18n 和暗色模式，还有一个官方容器镜像。因为一处结构上的不匹配和一个后果而被否决。
  那处不匹配：那些正本文档住在仓库根目录以及六个同级目录里，而 MkDocs 想要一个单一的 `docs_dir`
  —— 这意味着每次运行都要有一份暂存拷贝，于是"直接启动"获得了一个构建步骤。那个后果：首页会
  变成某个主题心目中的首页，而那张轴图、那个路线视图和那个镜像覆盖率徽章，每一个都会是一场和
  模板的搏斗。

- **VitePress 或 Docusaurus。** 比这里任何一个选项都更强。被否决，是因为在一个其余每一样可跑产物
  都是标准库 Python 或 POSIX shell 的仓库里，`node_modules` 是一个比一个被提交的包更大的异物 ——
  而且它更狠地过不了同一个零安装测试。

- **从 CDN 加载这些库。** 避开那 2.5 MB 的那个显而易见的办法。否决：它用一个大仓库换来一个在
  飞机上、在气隙环境里、或者在那个 CDN 挪了一个 URL 之后就不能用的 viewer。这个仓库的那些 lab
  是刻意纯本地、零依赖的；一个为了渲染一张图而往外打电话的 viewer，会是这里唯一一样自己站不住的
  东西。

- **在首次运行时去取这些库。** 那个折中方案，也是那个在被写下来之前看起来最好的：
  `site/vendor/fetch.sh`，把 `vendor/` 放进 `.gitignore`。被否决，是因为它**就是**一个安装步骤，
  只不过换了个名字，而且它恰好在那台"离线 viewer 本来最值钱"的机器上失败。

## 后果

- **工作树从大约 2 MB 长到大约 5.8 MB** —— 2.5 MB 的 vendored JavaScript 和 1.3 MB 的搜索语料，
  对着 2 MB 的真正写作。两个生成文件现在比一个人敲进去的一切都大，这件事值得知道，而且不值得去
  修。那对 vendored 的库应该基本永远不变；把版本钉死，并把一次升级当成它自己的一次提交。
- **有更多手写代码要去拥有** —— 一个路由器、一个分面导航器、一个搜索打分器、一个 Markdown 后处理
  器。横跨五个 ES module 大约 900 行，没有打包器，因为原生 module 从一个静态服务器上加载得很好。
- **搜索是一个生成文件，而生成文件会变陈旧。** `site/build-corpus.py --check` 在它陈旧时以非零
  退出，完全对应 `docs/build-index.py` 的契约，所以同一个习惯覆盖两者。
- **那条直接路径和那条容器路径，是同一份 URL 契约的两个实现**，而它们会漂移。`serve.py` 用一份
  从检索索引读出来的允许清单来强制它；`nginx.conf` 用文件扩展名和一条拒绝点文件的规则来强制它。
  Python 那个刻意是两者中更严格的，而两者都拒绝 `.git`。
