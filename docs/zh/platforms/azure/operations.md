> 以及 AI 怎么在那条运营循环里挣到它的位置（和那条[学习 ramp](ai-ramp.md) 不同）。

## 那份简报 —— "运维 Azure"意味着什么

在本地，运维意味着手放在硬件上：换盘、给机器打补丁、在数据中心里走。在 Azure 上硬件没了，而这份
工作往上挪：**你通过声明意图来运维，看着平台拿它做了什么，并让结果保持安全、可靠、负担得起。**
定义 day-2 工作的那三个问题：

- **它健康吗？** —— 而且你会在一位用户告诉你之前知道吗？（可观测性）
- **它安全吗？** —— 最小权限在**两个**平面上都还守着吗、没有东西暴露在外、没有东西在漂移吗？
- **它负担得起吗？** —— 没有被遗忘的资源在安静地计费，没有工作负载挂在错误的 SKU 或层级上吗？

下面的一切都是这三个问题，被落到实处。

## 运维笔记 —— 在 Azure 上什么会把你叫醒（以及什么应该）

那些真正产生故障的故障模式，其中大部分都在那条[共担责任线](architecture.md)的客户那一侧：

- **那个公开的 blob 容器** —— 私有数据被一个 Storage Account 上的匿名访问设置弄成了公开；那次
  典范式的 Azure 暴露。默认关掉公网访问，加上一条有人**真的去读**的 Defender for Cloud 发现
  （[`the-stack/07`](../../the-stack/07-security.md)）。
- **那份泄露的凭据** —— 一把被提交进仓库的存储**账号密钥**或者一个 service principal 的 secret，
  又或者一个永不过期的宽 **SAS token**。这**就是**为什么这个仓库讲 managed identity 和 RBAC 优于
  密钥（[`身份`](../../cross-cutting/identity-iam.md)）；CI 里的密钥扫描是基本盘。
- **"这个为什么够不到那个？"** —— 那个每日网络故障，带一个 Azure 转折：一条
  **同时在子网和网卡上被评估的 NSG** 必须**两处都**放行那份流量，而一条 **UDR** 能静默地把它黑洞
  掉。[`the-stack/02` 那架调试梯子](../../the-stack/02-network.md)原封不动地适用：

```mermaid
flowchart LR
  pkt["包：VM A 想够到 VM B"] --> nicA["A 网卡上的 NSG —— 出站放行吗"]
  nicA --> subA["A 子网上的 NSG —— 出站放行吗"]
  subA --> udr["route table / UDR —— 下一跳在哪"]
  udr --> subB["B 子网上的 NSG —— 入站放行吗"]
  subB --> nicB["B 网卡上的 NSG —— 入站放行吗"]
  nicB --> ok["到达 B"]
```

- **那份账单意外** —— 出网、跨 zone 流量、一台被遗忘的 **Bastion 主机**或 **NAT 网关**或 GPU VM
  （[`成本`](../../cross-cutting/cost.md)）。在 Azure 上，如果你设过，它以一条 **Budget 告警**
  把你叫醒；如果没设，它以一张发票把你叫醒。
- **本想区域冗余却成了单 zone** —— 一个"高可用"的服务，一切都在一个 zone 里，而它是在那次它本该
  熬过的 zone 故障当中被发现的（[`the-stack/01`](../../the-stack/01-physical.md)）。
- **那次 Entra 角色对 RBAC 的拒绝** —— 一个动作被拒绝，不是因为缺了一次授予，而是因为那次授予是在
  *错误的平面*上做的：你是一个 subscription Owner，却在试图做一件目录的活；或者你是一个 Global
  Admin，却从来没被给过资源访问权（[`architecture.md`](architecture.md)）。Azure 那个签名式的
  凌晨三点挠头时刻。
- **RBAC 范围漂移** —— 那个在 subscription（或者更糟，在 management group）上分配的角色，向下流得
  比任何人打算的更远，而它是在被滥用的那天被发现的。最小权限是一次持续的复审，不是一次性的授予。

## 那些运维活，拆开来看

一个 Azure 管理员反复要做的那些活，按**节奏**分解 —— 因为"这份工作到底包含什么"，最好由"你做什么、
多久做一次"来回答：

| 节奏 | 任务 | 面 | 它为什么要紧 |
| --- | --- | --- | --- |
| **持续（自动）** | Azure Monitor 对健康、延迟、错误率、预算告警；Defender for Cloud 的发现 | 可观测性、成本、安全 | 系统自己看着自己；你是被叫醒，不是被意外。 |
| **持续（自动）** | VM Scale Set 替换掉不健康的实例；开着自动修复 | 计算 | 牲口，不是宠物 —— 故障是被处理的，不是被守着的。 |
| **每日** | 分诊 Defender for Cloud 加 Sentinel 的告警；对真的那些动手 | 安全、可观测性 | 那些发现只有在有人读它并动手时才有用。 |
| **每日** | 回答"X 为什么够不到 Y"（NSG/UDR）和"这是谁干的"（Activity Log） | 网络、身份 | 那两个最基本的故障与审计问题。 |
| **每周** | 复审 RBAC：过宽的分配、`Owner` 分得太高、陈旧的 service principal | 身份 | 最小权限会衰减；这就是你怎么抓住那次漂移。 |
| **每周** | Cost Management 复审：异常、没打标签的花费、涨得最多的项 | 成本 | 在发票之前抓住那个被遗忘的资源。 |
| **每月** | 从利用率 rightsizing；重新审视预留 / 节省计划 / Spot | 成本、计算 | 多数 VM 配得过大，因为没人看过。 |
| **每月** | 给镜像打补丁/换代；用一个新的 Compute Gallery 镜像滚一遍 scale set | 计算、安全 | 关掉已知 CVE 的暴露面；重装优于就地打补丁。 |
| **每季** | 从一个 Recovery Services Vault 做恢复测试；真的核实 RPO/RTO | 存储 | 一份没测过的备份是一个希望（[`the-stack/04`](../../the-stack/04-storage.md)）。 |
| **每季** | 访问再认证；复审 Azure Policy 加 management group 护栏 | 身份、安全 | 证明那些护栏还守着；审计要证据。 |
| **有故障时** | 检测 → 遏制 → 根除 → 恢复 → 写那份复盘 | 全部 | 这整个仓库所关乎的那份判断；凌晨三点的那份镇定。 |
| **有变更时** | 一切走 Bicep/Terraform 加评审，不走门户 | 发放 | 门户是用来看的；变更走代码（[`iac`](../../cross-cutting/iac-and-config.md)）。 |

这张表让两件事变得可见。第一，**多数例行工作是自动的、或者本该是自动的** —— 人的活是分诊、复审和
判断，不是杂活。第二，**那个复审节奏（每周 RBAC、每周成本、每季恢复）是团队会跳过、然后后悔的那
部分** —— 它不光鲜，而它恰恰是漂移、超支和恢复不出来的备份藏身的地方，直到它们变成故障。

## AI 怎么协助运维工作（不只是学习）

[ai-ramp](ai-ramp.md) 那篇笔记讲的是*快速走到胜任*；这一节讲的是在你已经懂 Azure 之后，AI 在
*日常运营循环*里的位置。不同的活，同一门纪律：**AI 提供速度，判断提供真相。**

```mermaid
flowchart LR
  signal["一个信号：告警 日志 被拒动作 成本尖峰 报错"] --> ai["AI：解释 关联 起草那个修复或那条 KQL"]
  ai --> you["你：对着现实核实 决定 担起那个判断"]
  you --> act["动手：经 IaC 施加 跑那条命令 关闭那次故障"]
  act -.->|"下一个信号"| signal
```

AI 在运维里真正挣到饭钱的地方：

- **故障副驾 / 橡皮鸭** —— 把那条 Activity Log 条目、那次被拒绝的动作、那条 `az` CLI 报错贴进去：
  *"这是什么意思，你接下来会查什么？"* AI 在把一个晦涩信号变成一个假设上很快 —— 而你去测那个假设。
- **写 KQL** —— 这是一个值得倚重的、真实的 Azure 强项。*"一条在 Log Analytics 上按 URL 找出过去
  一小时 5xx 尖峰的 KQL 查询"*，或者一条给 **Sentinel** 用的、针对某个可疑登录模式的狩猎查询。
  AI 写 KQL 很流畅；在你相信那个结果之前，拿已知数据去做一次合理性核查。
- **日志与指标分诊** —— 归纳一个吵闹的日志窗口、把相似的错误聚在一起、把异常浮出来。对一堆没人想
  滚动的量做一次很强的初筛。
- **把修复起草成代码** —— *"关掉这条发现的 Bicep / Terraform / Azure Policy 变更"* —— 作为一份
  走正常 IaC 闸门的、可评审的初稿，绝不是一次 AI 说服你去做的门户变更。
- **事后写作** —— 把时间线变成一份复盘初稿；由你去纠正因果并担起那些结论。

在运营循环里 AI **绝不能**被信任的地方 —— 这里比在学习里赌注更高，因为这些是对着生产跑的：

- 它会**自信地误读一次被拒绝的动作** —— 当真正的问题在 *Entra 平面*时它可能去怪那次 RBAC 分配，
  或者当另一层才是拦截者时它去怪其中一个 NSG。仲裁者是现实（一次重跑、一份 flow log、那个
  effective-access 面板）。
- 它会**发明不存在的 `az` 参数、resource provider 属性和 RBAC 角色名** —— 在跑任何会改变状态的
  东西之前先核实。
- 它会**起草宽松的修复** —— 一条"为了让它能用"的 NSG 规则，打开了 `0.0.0.0/0`；或者在 `Reader`
  就够的地方给了 `Owner`。每一份 AI 起草的修复都要手动收紧。
- 它**拥有不了这次故障。** AI 加速那次查找和那份初稿；那个决定、那个爆炸半径判断，以及凌晨三点的
  那份问责，都留给你。

那条让它保持安全的规则：**AI 碰信号和初稿；你碰生产。** 任何 AI 建议的、会改变状态的东西，都走和
你自己的变更同一道评审加 IaC 闸门 —— 那条"门户是用来看的"纪律
（[`iac`](../../cross-cutting/iac-and-config.md)）对 AI 的建议和对你自己的建议一样适用。

## 诚实边界

这里那门运维**纪律**是 🔨 —— 分诊、故障方法、那个复审节奏、最小权限复审、恢复测试、把成本和漂移
当成信号 —— 因为它是同一门从真实基础设施和机队工作里带过来的运维手艺，而在那里传呼是真的会响的。
**身份那一片是双重的 🔨**：在 Activity Log 里读一次被拒绝的动作、并把那两个权限平面理清，恰恰就是
我亲手做过的那片 Entra/RBAC 地面（[`身份`](../../cross-cutting/identity-iam.md)）。Azure 服务其余
的那些细节（哪个面板、哪条告警、哪种发现类型）是那条 🧭 ramp，按这个仓库的方法测绘并验证过。
这里的声称不是"为一片生产 Azure 估算面背了多年 on-call"；而是一份**可迁移的运维纪律，加上一条通向
Azure 那套工具的、快速而诚实的 ramp** —— 而身份已经很深。
