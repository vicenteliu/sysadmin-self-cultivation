# GCP —— 那条 AI 辅助 ramp

> 怎么在几天里在 GCP 上走到*胜任* —— 用 AI 当副驾，并且让它保持诚实。GCP 是证明这套方法最干净的
> 地方，因为它有那么大一部分是那些已经在 AWS 和 Azure 上映射过的面的一次改名。这条 ramp 基本就是
> 去找那几个**不是**改名的地方。

[`WHY.md`](../../WHY.md) 的那个前提：一个有经验的管理员加上 AI，能在几天里就在一个从没碰过的平台上
干活。在 GCP 上那几乎是字面意义上成立的 —— 那七片面和 AWS 的几乎一模一样，所以这份活不是从零学一朵
云，而是**翻译一朵你已经会的，并抓住 Google 做了不同选择的那四个地方。** AI 在翻译上非常出色、
在细节上很危险，所以方法还是那两门被扣在一起的纪律：**AI 提供速度，判断提供真相。**

## 那条循环（GCP 口味）

对任何一个新领域（比如网络）：

1. **锚定到你已经知道的东西上。** 不是"教我 GCP 网络"。而是：*"我懂 AWS 的 VPC、subnet、
   security group 和本地 TCP/IP。把 GCP 网络映射到那上面 —— 什么是一样的、什么被改了名，
   以及什么是真的不同？"* 那个答案几分钟内就把那个全局 VPC 异类浮了出来。
2. **先猎那些结构性异类。** GCP 有四个地方会让 AWS 反射失效 —— 把注意力花在这里，别花在那 90%
   一模一样的部分上：
   - **全局 VPC** —— 一个网络横跨多个 region；subnet 是区域级的；多区域"只是路由"，不需要
     peering（[`the-stack/02`](../../the-stack/02-network.md)）。
   - **Project / 组织层级** —— project 是那个账号/爆炸半径单位，不是一个标签；那棵组织树是护栏面。
   - **自定义机型** —— 把 vCPU/内存拨到准确数值，而不是从一份菜单里挑一个尺寸。
   - **以 service account 为中心的 IAM** —— role 在资源层级上绑定到 member 上；service account 是
     那个默认的工作负载身份。
3. **拿到那 80/20。** *"在 GCP 网络里，一个管理员每天用的是哪两成，而我可以推迟哪些？"*
   现在你能排优先级了。
4. **生成那个产物。** *"给一个带两个区域级 subnet 和一条瞄准某个 service account 的防火墙规则的
   全局 VPC 写 Terraform"*，或者 *"让这个 service account 只读一个桶的那条最紧的自定义 IAM 角色"*。
   几秒钟出第一稿。
5. **核实 —— 那个不容商量的步骤。** 对着**当前的 GCP 文档**交叉核对每一个角色名、每一个 API、
   每一个参数。GCP 的角色目录很大，而 AI 会在里面自信地猜；假定那份初稿九成是对的，然后去猎那一成。
6. **在一个带预算告警的沙箱里跑它。** 现实是最后那位评审者 —— 一份 `terraform apply` 得下去、
   并且能被干净 `destroy` 掉的栈，胜过任何解释。
7. **让 AI 反过来评审它。** *"这是我的 Terraform / 我的 IAM binding —— 我漏掉了什么安全或成本风险，
   以及我把那个全局 VPC 模型用对了吗？"*

## 那些真能挣到饭钱的提示词模式

- **翻译者：** *"在我已经懂 AWS/Azure 对应物的前提下解释 X —— 只讲 GCP 特有的那部分差量。"*
  （在 GCP 上完全跳过那份新手税。）
- **异类猎手：** *"在这一点上 GCP 的模型和 AWS 真正不同在哪，以及我的 AWS 直觉会在哪儿给我错误
  答案？"*
- **80/20：** *"关于 X，我必须理解的最小集合是什么才算能干活，而什么可以安全地推迟？"*
- **最小权限生成器：** *"恰好只做这件事的那条最紧的自定义角色 / IAM binding。"*（然后手动收紧。）
- **评审者 / 橡皮鸭：** 把一条报错、一段 `gcloud` 输出、一次被拒绝的请求贴进去 ——
  *"这是什么意思，我该怎么调它？"*

## AI 会烧到你的地方（所以这些验得最狠）

- **IAM 角色与权限** —— GCP 的目录非常庞大；AI 会发明不存在的角色名和权限字符串。去核那份角色参考。
- **那个全局 VPC** —— AI 是在 AWS 内容偏多的文本上训练的，它会递给你**区域模型的（AWS 形状的）
  网络建议**去用在 GCP 上；每一次都要抓住它。
- **资源层级** —— 它会把 **project 对 folder 对 org** 搅在一起，也会搞错一条策略或一个配额实际
  作用在哪一级。
- **机型、配额和价格** —— 全都在漂；核实当前数字，绝不要引用 AI 给的。
- **任何关乎安全的东西** —— 桶访问（统一访问对旧式 ACL）、密钥策略、防火墙暴露面。核实并测试，
  绝不要凭信任发布。

## 为什么这是一项**系统管理员的**技能，而不是一条绕过它的捷径

AI 能在几秒钟里生成一个全局 VPC。它没法告诉你，你那台实例上不了网是因为那条防火墙规则瞄错了
service account，或者你在一个区域级资源之下把两个副本放进了同一个 zone。它拥有不了凌晨三点那次
故障。那份判断 —— 最小权限的直觉、"这个为什么够不到那个"、读懂那次失败、在成本和可靠性之间权衡 ——
才是那门手艺，而不管控制台上写的是 AWS 还是 GCP，它都是同一门手艺。AI 只是把"**拥有**那份判断"和
"把它**施加**到 GCP 那些名字上"之间那些死记硬背移走了。

那就是那整个论点，落在第三朵云上：**心智模型是那份资产；从 AWS/Azure 到 GCP 的那次翻译，是 AI
最明显地成为一个加速剂的地方；而核实那四个异类，是让它变安全的那门纪律。**
