## 那份简报 —— "运维 vSphere"意味着什么

你通过让一池硬件保持健康、均衡、可恢复，同时让它上面那些 VM 保持在线，来做运维。那三个 day-2
问题：

- **它健康吗？** —— 主机连着、datastore 有余量、没有资源争用，而你会在一位用户注意到之前知道吗？
- **它安全吗？** —— 权限是最小的、主机加固过了、该加密的 VM 加密了吗？
- **它高效吗？** —— VM 尺寸合适、DRS 在均衡、容量走在需求前面吗？

## 运维笔记 —— 在 vSphere 上什么会把你叫醒

- **那个满掉的 datastore** —— 它上面每一台 VM 同时停掉；那个最可预防的单一 vSphere 故障
  （[`the-stack/04`](../../the-stack/04-storage.md)）。把剩余空间当成一条一等告警来监控，
  并盯着快照的增长 —— 一个被遗忘的快照会静默地把一个 datastore 填满。
- **那次 HA 事件** —— 一台主机死了，而 HA 把它的 VM 在别处重启了（一次重启量级的中断）。那是 HA
  **在起作用**（[architecture](architecture.md)）—— 那次故障是那台死掉的主机，而那份响应是在这个
  集群失去它的 N+1 之前把它换掉。
- **vMotion / 维护模式失败** —— 一台主机疏散不了，因为某台 VM 有一个主机本地设备、CPU 不兼容，
  或者它的磁盘没有共享存储。维护窗口依赖疏散能成；在那个窗口之前先搞清楚那些前提。
- **资源争用** —— 那次"什么都很慢"的故障，要在正确的指标里读：**CPU ready**（VM 在等物理 CPU
  ＝ 超配）、**内存 ballooning / 交换**（主机内存压力）、**datastore 延迟**（存储争用）。
  "慢"不是一个诊断；那个计数器才是。
- **一台死掉的主机** —— 硬件故障在这里是你的传呼，不是某个厂商的；备件和一条重建路径是那门
  [self-host](../self-host/README.md) 纪律，往上一层。
- **那个被遗忘的快照** —— 快照不是备份，而且它们会长；一台被留在快照上好几周的 VM，是一次正在等着
  发生的性能与 datastore 空间故障。

## 那些运维活，拆开来看

一个 vSphere 管理员反复要做的那些活，按**节奏** —— 因为"这份工作包含什么"，是由"你做什么、多久
做一次"回答的：

| 节奏 | 任务 | 面 | 它为什么要紧 |
| --- | --- | --- | --- |
| **持续（自动）** | vCenter 对主机健康、datastore 用量、HA 事件的告警 | 可观测性 | 是这个集群在一位用户之前告诉你。 |
| **持续（自动）** | DRS 均衡负载；HA 待命随时重启 | 计算 | 故障是被处理的，不是被守着的。 |
| **每日** | 分诊告警；检查集群健康、datastore 余量、快照增长 | 可观测性、存储 | 那次满 datastore 的故障要么在这里被抓住，要么根本抓不住。 |
| **每日** | 回答"这台 VM 为什么慢" —— CPU ready / ballooning / datastore 延迟 | 计算 | 那个最基本的争用故障。 |
| **每周** | 复审权限（陈旧的授予、过宽的角色）；快照卫生 | 身份、存储 | 最小权限和 datastore 空间都会安静地衰减。 |
| **每月** | 从性能数据给 VM 做 rightsizing；回收超配的 CPU/内存 | 计算 | 多数 VM 配得过大，因为建成日之后没人再看过。 |
| **每月** | 经 Lifecycle Manager 给 ESXi 主机打补丁 —— 滚动、维护模式加疏散 | 安全 | 在不停 VM 的情况下关掉主机 CVE ——*前提是*疏散能成。 |
| **每季** | 从备份测试一次 VM 恢复；核实 RPO/RTO | 存储 | 一份没测过的备份是一个希望（[`the-stack/04`](../../the-stack/04-storage.md)）。 |
| **每季** | vCenter 升级规划；容量复审（N+1 还成立吗？） | 生命周期、容量 | 这个集群长大了；证明它仍然丢得起一台主机。 |
| **有故障时** | 检测 → 缓解（vMotion 挪走 / 重启）→ 解决 → 复盘 | 全部 | 那门[故障纪律](../../cross-cutting/incident-response.md)，在你自己拥有的硬件上。 |

这让两条真相变得可见：**多数例行工作是自动的（DRS/HA/告警）—— 人的活是分诊、容量和判断**；
以及**那个复审节奏（权限、快照、rightsizing、恢复测试）是团队会跳过、然后后悔的那部分** ——
那是漂移、被浪费的容量和恢复不出来的备份藏身的地方。

## AI 怎么协助运维工作

和那条[学习 ramp](ai-ramp.md) 不同 —— 这是*日常循环*里的 AI，在一个你已经懂的平台上，
所以**AI 起草，你的专业去核实**：

```mermaid
flowchart LR
  signal["一个信号：告警 性能图 PowerCLI 报错 事件日志"] --> ai["AI：解释 关联 起草那段 PowerCLI"]
  ai --> you["你：对着现实核实 决定 担起那个判断"]
  you --> act["动手：跑那个 cmdlet 疏散一台主机 关闭那次故障"]
  act -.->|"下一个信号"| signal
```

- **起草 PowerCLI** —— *"一条 PowerCLI 单行命令，列出每一台带着超过 7 天快照的 VM"* ——
  AI 几秒钟就写出来，而因为你懂 vSphere，你立刻就能抓住那个错的 cmdlet。
- **告警 / 日志分诊** —— 归纳一条吵闹的事件流、把相似的告警聚在一起、把异常浮出来；一次你随后
  去确认的快速初筛。
- **AI 绝不能被信任的地方：** 它会**发明 PowerCLI 的 cmdlet 和参数**；它会**记错版本相关的行为和
  授权**；而且它会自信地把一个争用症状解释错。那道护栏就是这个仓库那条规则 ——
  **AI 碰信号和初稿；你碰生产** —— 而在这里，"你"是一个以前真的跑过这个的人。

## Lab —— N+1 是一个会衰减的数字 ✅ 可跑

**亲手证明 HA 的算术。** 一个纯本地、只用 stdlib 的 drill，把[架构篇](architecture.md)的集群往
时间前方推：六台主机、五百台 VM 在一次主机损失后跑在 78%，然后是一年的增长、那句*就是*保证的拒绝、
把它关掉的那次点击，以及下一次主机损失让十台 VM 没有地方可去 —— 上面那条*在集群失去 N+1 之前把死掉
的主机换掉*的规矩，落到实处。

```bash
python3 platforms/vsphere/labs/n-plus-one-decays/n_plus_one_drill.py
```

exit `0` 表示五条教训都成立（兼作 CI 检查）。见 [`labs/n-plus-one-decays/`](labs/n-plus-one-decays)。

## 诚实边界

🔨 **亲手做过的深度。** 那些分诊直觉、那份争用指标素养（CPU ready、ballooning、datastore 延迟）、
那套维护模式加疏散的节奏、那份快照纪律，以及那个恢复测试的习惯，都是生产经验 —— 区域 vCenter
管理、VCP6-DCV/NV。这就是这个仓库带到其他平台上去的那门运维纪律。唯一的 🧭：那些**最新的
vSphere 8 工具**（Lifecycle Manager 镜像、vROps/Aria 的细节）和**后 Broadcom 授权** ——
对着当前文档核实过，不被声称成当前版本的生产经验。
