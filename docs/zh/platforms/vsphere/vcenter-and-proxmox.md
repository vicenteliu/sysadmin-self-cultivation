# vCenter 与 Proxmox —— 到底哪儿不一样

## 控制平面住在哪，以及它死掉的时候你失去什么

这是那个生成了其余大部分差别的差别，而功能对比表从来不提它。

**vCenter 是一个东西。** 它是一个独立的 appliance，它*就是*那个管理平面，而且它几乎总是作为一台
虚拟机跑在它所管理的那片估算面上。丢掉它，那些主机继续跑、那些 VM 继续服务，而你失去编排：没有
vMotion、没有 DRS 决策、没有集中认证、没有那个被你接了一堆东西上去的 API。你得先恢复它，才能做别的
任何事。

**Proxmox 的控制平面是那个集群。** 每个节点都跑着那套管理栈，它们通过一个借自 Linux HA 世界的
quorum 协议达成一致。没有一个 appliance 可以丢。你能丢掉的是 **quorum** —— 而一个掉到 quorum 以下
的集群会拒绝做任何变更，那正是你想要的行为，也正是一个两节点集群第一次丢掉一个节点时会让所有人吃惊
的那个行为。

**所以这两种故障模式是相反的形状。** 一个是一个单一组件，丢了它你就失去动手的能力。另一个是一份
分布式共识，丢了它你也失去动手的能力。第一个靠恢复一样东西就能修好，而它是一个**循环依赖** ——
那个管理平面是它所管理的那片估算面的一个 guest，这和
[一把恢复密钥被存在它本来要绕开的那个身份后面](../../endpoint/encryption-and-keys.md)
是同一个形状。第二个不需要任何恢复，它需要的是你在建它之前就想过节点数。

**那个实践后果，只说一次：** 不管你跑哪一个，把"在管理平面不可用的那一天，你怎么管理这片估算面"
写下来，并且测试它。那句话是整篇笔记里可迁移的那部分。

## 它们真正分岔的那四个面

不是一张对比表 —— 是各自逼你做的那些决定。

**存储。** vSphere 给你一个专门做的集群文件系统和一个集成的超融合选项，而那些决定是关于 datastore
布局和策略的。Proxmox 递给你整个 Linux 存储生态 —— 一个节点上的 ZFS、跨集群的 Ceph、LVM、纯目录
—— 而那个决定是*选哪一个*，这是一个比它看起来大得多的问题。**Proxmox 那边要求你懂存储；vSphere
那边要求你懂它的存储。** 哪个都不更容易；只是那些技能的迁移方式不同。

**网络。** 分布式交换，加上那个网络虚拟化产品之后是一个带策略的 overlay。Proxmox 那边是 Linux
bridge 或者 OVS，按你配置任何一台 Linux 主机的方式去配，再加上你在上面自己建的东西。还是同一个
形状：一个是你要学的产品，另一个是你如果懂 Linux 就已经懂的底料 —— 这也是为什么对一支有 Linux
深度的团队来说，这次迁移比它的名声要容易。

**集群与迁移能力。** 两边都有热迁移。自动放置和负载均衡在一边是一等的产品功能，在另一边是你自己
攒出来的东西。**如果没有人真的在用自动放置 —— 而在非常多的估算面里没有人在用 —— 这个差别不花你
一分钱。** 在给它定价之前先搞清楚。

**授权与支持姿态。** 🧭 **这里是 ramp，而它被标出来了。** Broadcom 之后的那片局面是这个问题之所以
被问起的最常见的单一原因，而它变得比一份写下来的文档追得上的还快。这篇笔记会说的是那份持久的一半：
一次订阅制对永久授权的变更是一次*采购*事件，它之所以变成一次*架构*事件，只因为它逼出了一次没人
排过期的重新评估。当前条款你自己去读；别在这里读。

## 什么真正在跟这次迁移较劲

那些 VM 是容易的部分。下面是那个已交付的评估器所施加的那套规则，而它值得被当成一份对现实的描述来
读，而不是当成一个工具的配置：

| 严重度 | 它找出什么 | 为什么是这个严重度 |
|---|---|---|
| **Hard** | 一个 raw device mapping | 没有直接的等价物。那份存储需要一次重新设计，不是一次转换 |
| **Hard** | 一个已终止支持的 Windows guest | 那些半虚拟化驱动对它不存在。你是在传统设备变通和重建那个 guest 之间做选择 |
| Moderate | 存在快照 | 快照链不转换。先合并掉，而那是一个没人预算过的维护窗口 |
| Moderate | 一个现代 Windows guest | 驱动必须在切换之前或者切换时装进去。完全做得到，也完全是一件逐 VM 的活 |
| Minor | 一个 Linux 上的非 virtio 网卡 | 型号会变，而那个驱动已经在内核里了 |
| Minor | EFI 固件 | 用匹配的固件重建，并检查 Secure Boot 的预期 |
| Minor | 超过几个 TB | 一个传输窗口，不是一个技术问题 |

**注意那份清单上*没有*什么。** 那个 hypervisor。这次迁移里没有任何一件事是*因为换了一个
hypervisor* 才难 —— 那些 Hard 发现是没有对应物的存储抽象，和老到没有驱动的 guest。那是值得带走的
那个发现：**一次 hypervisor 迁移是一个穿着 hypervisor 外衣的存储与 guest 支持项目。**

## 还有评估器打不了分的那部分

每一台 VM 都可以是 EASY，而这次迁移仍然会失败，因为接在 vCenter 上的那样东西不是那些 VM。

**是所有握着它那个 API 的东西。** 带 vSphere 集成的备份软件。带一个 vCenter collector 的监控。
那套发放 VM 的自动化。那个认为自己权威的 CMDB。那些自从写它们的人离职之后就没人读过的脚本。
**这里面每一个都是一次单独的迁移，它们没有一个会出现在一份 VM 盘点里，而它们加起来通常是这活的
大部分。**

所以那个诚实的第一步不是一份 VM 的盘点。它是一份**会向 vCenter 认证的东西**的盘点 —— 这和
[没人去数的那些非人身份](../../the-reference-office.md#why-these-numbers)
是同一个问题，只是对着一个系统问的，而它有同一个答案：这份清单比任何人预期的都长，而且没有任何东西
在维护它。

## 这对参考办公室意味着什么

什么都不意味着，而那正是那个有用的答案。[那间参考办公室除了一个 staging 环之外不跑任何 VM
估算面](../../the-reference-office.md#本地--什么不能离开) ——
装机在厂商那儿、文件在一个租户里、身份在一朵云上，就没有什么东西需要一个 hypervisor 集群去托管了。
**一间一百人的办公室在问这个问题，通常是在问一个它继承来的问题**，而第一步动作是先搞清楚那片估算面
上到底在跑什么，再去比较那些拿来托管它的平台。

这个问题真实存在的地方是再大一档，或者在一片有理由把算力留在本地、而这间办公室没有那个理由的估算面
里 —— 那恰恰是这间办公室所施行的
[那三条测试](../../the-reference-office.md#本地--什么不能离开)，
对着一组更大的需求去跑。

## 诚实边界

🔨 **vSphere 那一侧很深。** 作为一名区域级的 vCenter 管理员运维过，维护并升级 VM 基础设施与服务；
持 VCP6-DCV 与 VCP6-NV 认证。上面那些控制平面故障行为是运维出来的，不是读来的。

🔨 **Proxmox 与 KVM 那一侧是相邻而且真实的** —— 包括物理 GPU 直通 —— 在 lab 和内部环境里，而不是
作为这位作者自己的一片生产估算面。这个区别要紧，也正是为什么这篇笔记的标记是 `mixed` 而不是 🔨：
**vSphere 那一半是生产的地面；Proxmox 那一半是真的动过手，赌注小一些。**

🧭 **Broadcom 之后的授权与支持局面**，以及最新的 vSphere 与 NSX 功能。测绘并验证过，绝不虚张，而且
刻意不在这里引述，因为它过期得比这个文件能被维护的速度还快。

**不声称：** 在生产规模上跑一片 Proxmox 估算面、规模上的 Ceph 运维，或者关于一个组织该选哪个平台的
任何断言。
