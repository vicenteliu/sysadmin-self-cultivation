# Lab 06 —— 没有数据不等于健康

> 🌐 **语言：** [English（默认）](../../../../../the-stack/labs/06-no-data-is-not-healthy/README.md) · **中文**

> **输入：** 无 · **输出：** 谁被呼到了、什么时候、被什么呼的 · **风险：** 无 —— 不用服务、
> 不用 exporter、不用凭据 · **root：** 不需要

**目标：** 把[第 06 章](../../06-observability.md)警告过、而没有任何一块仪表盘的形状能展示出来的
那个故障变得摸得着 —— **那次产出沉默、而不是产出一次呼叫的故障。**

一套正常监控栈里的每一条告警，都是一个作用在"已经到达的数据"上的谓词。那是一个扎实的设计，而它恰好
有一个盲区：

```
a threshold alert   fires when a number crosses a line
no data             is not a number, so it crosses nothing
a monitor inside    the failure domain it watches stops sending at the same
                    instant its target stops serving
```

**你会练到：** 把[第 01 章](../../01-physical.md)那条放置规则，施加到那个负责告诉你第 01 章的东西
身上；以及对"缺席"告警，而不是对"数值"告警。

## 这个 lab 为什么是纯本地的

那一章的引导式走查会立起 Prometheus、Grafana 和一条 OTel trace，定义一个 SLO 并把错误预算烧光。
去做它 —— 它够得到真实的基数和一份真实的账单，而那是任何模型都做不到的。但它底下那个发现是一个
关于*那个监控本身在哪个故障域里*的问题，而你没法在一个试用账号上给一个机柜断电。

三个监控、一个小时，以及一个在第 12 分钟失去供电的机柜。不用服务、不用 exporter、不用凭据、
不用 `pip install`。Python 标准库，CI 也跑得了。

## 跑它

```bash
python3 the-stack/labs/06-no-data-is-not-healthy/silence_drill.py
```

exit code `0` 表示关于这个教训的每一条断言都成立。

## 你会看到什么

1. **第 12 分钟，以及第 20 分钟时每个监控在报什么。** 那个在机柜内的监控，在它的目标死掉的那一
   瞬间就停止发送了 —— 它和它所监控的那个故障域是同一个。那个在机柜外的，正在报告用户真的在遇到
   的那些错误。

2. **谁被呼到了。** 那条机柜内的错误告警**从来没有触发**：它是一个作用在数据上的谓词，而没有数据
   到达。那条机柜外的症状告警在第 14 分钟呼了人 —— 也就是用户注意到的那一分钟。

3. **那条 cause 告警，也就是多数估算面实际拥有的那一条。** CPU 一直到断电为止都是 0.35，断电之后
   就没有上报了。**不存在任何一个 CPU 阈值能逮住这次故障** —— 调它不是解法，也从来不是。

4. **唯一逮得住一个域内监控的控制。** 一条 staleness 告警 —— 一个 dead-man's switch —— 在第 15
   分钟对着样本的*缺席*呼了人。这个文件里别的每一条告警都在问一个关于数字的问题；这一条问的是
   "到底有没有过一个数字"，而这正是它为什么是唯一一条能活过它自己的主体死亡的告警。

5. **第 20 分钟仪表盘显示什么，以及它为什么没有撒谎。** 两块绿色面板，各自显示着它被告知的最后
   一样东西，已经过时九分钟。而用户已经拿了六分钟的错误了。**绿色和沉默是同一个颜色。**

## 验证（别光信这个脚本说的）

```bash
python3 silence_drill.py --sabotage no-data-is-green      # exit 1
python3 silence_drill.py --sabotage cause-alerts-suffice  # exit 1
```

`no-data-is-green` 把沉默当成健康 —— 也就是一个 UI 做的事 —— 而挂掉的是那条 staleness 断言，因为
它是唯一一条曾经依赖于这个区分的断言。

`cause-alerts-suffice` 让每一个监控都去测量一样在用户受苦时不会动的东西 —— 也就是那种对资源告警、
然后管它叫可观测性的估算面。机柜外那条告警不再呼人，而这次运行里别的什么都没变：故障照样发生、
仪表盘照样是那个样子，而没有人被告知。

想再往前一步，把 `errors-in-rack` 挪到 `rack-b` 再跑一遍。它会在第 14 分钟呼人，而那条 staleness
告警从来不触发 —— 这次放置变更让那个 dead-man's switch *对那个监控而言*变成冗余的了，而这正是修
这些问题的正确顺序。

## 重点

**你会遇到的最糟的那个小时，是那个根本不产出任何数据的小时。**

两件要带走的事：

- **把监控放在和它所监控之物不同的故障域里。** 这就是第 01 章那条反亲和规则，被施加到那个"负责
  告诉你第 01 章"的系统身上 —— 而它几乎被普遍地跳过，因为一个监控感觉像基础设施，而不像一个工作
  负载。
- **对数据的缺席告警。** 一条 staleness 告警不光鲜、很少触发，而且是这片估算面里唯一一条输入不是
  数值的谓词。你拥有的别的每一条告警，都已经同意了对这件事保持沉默。

还有第三件，是那件值得在复审上大声说出来的：*一块绿色的仪表盘是一句关于最后一个样本的声称，不是
一句关于「现在」的声称。* 去问任何一块面板，它上一次听到消息是什么时候。
